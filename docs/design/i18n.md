# Interface languages

Status: rule from the first screen. English is the default; Brazilian Portuguese is the second
language (ADR 0025).

- Every text a person reads or a screen reader announces (labels, `aria_label`, tooltips,
  placeholders, toasts, window titles) comes from `apps/cloudrs/src/i18n`, one module per area
  (`i18n::player`, `i18n::search`…). Never a string literal in a screen.
- Same approach as xemnas:
  - `strings!` generates `fn name() -> &'static str`;
  - `formats!` generates `fn name(args) -> String`, with named arguments inside the literal
    (`"{count} tracks"`) so each language can reorder them;
  - a missing translation is a compile error.
- Cost: one atomic read and a `match` per string. No allocation, map or file read at runtime.
- Content is never translated: track titles, artist names, descriptions and comments are shown
  as SoundCloud returns them.
- Dates, relative time and number formatting follow the selected language. Numbers go through
  `i18n::number` (see "Numbers" below).
- The language is a saved setting (ADR 0017). `Language` lives in `sc-core` and
  `i18n.rs` re-exports it; the app calls `i18n::set` with the saved value before the window
  opens and whenever the core echoes a change.
- The picker in Settings has one pill per language, each written in its own name ("English",
  "Português (Brasil)"), so it can be found whatever the interface shows.
- With nothing saved (a first run), the language follows the system's (`sys-locale`): any
  `pt*` locale gives Brazilian Portuguese, anything else English. A saved choice always wins.

Adding a language: add its tag to the `Language` enum, add its field to both macros (they
require one text per language, so the compiler stops at the entries that lack it) and fill in
every `strings!`/`formats!` entry. The compiler reports only the first missing entry in each
block, so it takes several rounds. Also add the language's name in itself to
`i18n::language_name`.

## Numbers

`i18n::number::compact` and `one_decimal` write numbers the way the language does:

| | English | Brazilian Portuguese |
|---|---|---|
| thousands | `1.2K`, `12K` | `1,2 mil`, `12 mil` |
| millions | `3.4M` | `3,4 mi` |
| one decimal | `1.5` | `1,5` |

## Text kept by widgets

Text drawn in `render` follows a language change by itself. A few widgets keep the text they
were built with (the placeholders and hint of a `SearchField`, the window titles, the tray menu).
`Shell::relabel` writes them again when `Event::Settings` brings another language; a new widget
with fixed text must be added there.

## Adding or reviewing a language

Each `strings!`/`formats!` entry has one field per language (`en:`, then `pt_br:`…). Keep every
named argument of a `formats!` entry (`{count}`, `{name}`) and the same Unicode escapes as the
English (typographic quotes, apostrophe, ellipsis).

- The compiler reports only the first missing entry in each block, so expect to rebuild several
  times; `grep -c` the entries of a module to see what is left.
- A native speaker reviews the texts before they ship.
- Texts grow about 30% in Portuguese: check truncation on buttons, pills, tooltips and the
  mini player.
- Tone: "você", short sentences, like the English.
